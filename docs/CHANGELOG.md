## 26H2 Build 17（2026-09-15 · 悬浮球清晰度 + 托盘菜单定位）

### 修复
- **悬浮球发虚**：球体自身挂着 `DropShadowEffect`。Effect 会把控件（渐变 + 1px 白描边 +
  「摇」字）**先渲染成一张中间位图再合成**，而球还要被缩放动画（悬停 1.06 / 抽中弹跳）
  和窗口移动反复重采样 ⇒ 看着就是"糊"。改法与本项目此前修「按钮文字模糊」时一致：
  **投影交给一层独立的纯色 Border**（它没有细节可丢），球体本身不再挂 Effect；
  窗口内容补 `UseLayoutRounding` / `SnapsToDevicePixels`；
  所有 `Left/Top` 赋值统一走新的 `MoveTo()`，把窗口**吸附到整数设备像素**
  （125% 缩放下 1 设备像素 = 0.8 DIP，小数位置会被 DWM 重采样）。
- **托盘右键菜单跑到屏幕左上角**：这个毛病先后修过三次（用 MainWindow 当锚点 →
  改用常驻 1×1 透明宿主窗口 + `PlacementMode.AbsolutePoint`）都没根治。
  根因是 **Popup 的绝对定位本身就不可靠**：真正决定位置的是 WPF 的 popup 定位引擎，
  它依赖锚点的 PresentationSource 与锚点所在显示器的 DPI 上下文，在"主窗口已隐藏 /
  跨显示器 / 缩放非 100%"的组合下会退化成 (0,0)。
  现在 `ModernMenu` 改为**真实 Window**：`Left`/`Top` 由系统直接摆放，我们算出来的
  DIP 坐标就是最终位置，完全不经过定位引擎。悬浮球右键菜单同样受益。

### 自检（本轮的重点改进）
- 之前"托盘菜单"相关断言读的是 `LastScreenOffset` —— **我们自己算出来的目标值**。
  旧实现里目标值一直是对的，是 Popup 没照着摆，于是自检 43/43 全绿、用户看到的菜单
  却在左上角。**教训：别断言自己假设可靠的中间信号，要断言最终产物。**
  现在一律改用 **Win32 `GetWindowRect` 读真实屏幕矩形**做断言：
  - `2a` 菜单右/左边缘必须贴合托盘图标 x（直接抓"跑到左上角"这个现象）
  - `2b` 菜单底边必须在图标上方，且完整落在屏幕内
  - `3b` 主窗口隐藏后（"关闭到托盘"）同样成立
  - `4c` 球体自身不得挂 Effect、投影层必须挂、两层必须共用同一个变换
  - `4d` 窗口必须落在整数设备像素上
- 结果：**42/42 PASS**（实测环境 1920×1080 @125% 缩放）。

## 26H2 Build 18（2026-09-16 · 开机自启动两项修复）

用户报「覆盖安装新版本后，开机自启动会弹两个实例正在运行的提示但程序起不来；
且所有设备上勾选开机自启动后，重进设置页又变回未勾选」。两条根因都已定位并修好。

### ① 勾选状态丢失（所有设备都中）
`AutoStart.IsEnabled()` 把 Run 值 `"C:\...\LuckyPicker.exe" /min` 直接
`Trim('"',' ')` 之后**当作路径**去比较。Trim 只去掉**首尾**的引号/空格，
尾部会残留 `" /min` ⇒ 与真实路径**永远不相等**、`IsEnabled()` **永远返回 false**。
所以设置页每次打开都显示未勾选（悬浮球右键菜单里的勾选态同理）。
现在改为**先把被引号包住的 exe 路径解析出来**再比较。

### ② 开机弹「已在运行」但程序不启动
两层原因叠加：
- **值名不统一**：WPF 安装器早期把 Run 值名写成中文的 `YBH幸运摇人器`，
  而主程序写 `YBHLuckyPicker` ⇒ 两个值名并存 ⇒ 开机**把程序拉起两次**。
- **竞态判据**：`App.OnStartup` 里那句「同名进程去重」（`others > 0` 也判定为已在运行）
  是 Build 15 加的"双保险"，但两个实例几乎同时启动时**各自都能看到对方进程**
  ⇒ **双双弹窗并退出，结果谁都起不来**。

修复：主程序与安装器统一用 `YBHLuckyPicker`；安装/卸载/开关自启动时都**清理遗留值名**；
主程序每次启动也清一次（老用户跑一次新版本即自动恢复）。单实例判据回归
**命名互斥体**这一个权威来源，进程数只留作诊断日志。
